# 2026 R2 campaign results: the files behind the main page

These files belong to the measurement campaign `158169ad-ebb1-4c0a-920d-84a8eb311cea` (Acumatica 2026 R2, build 26.200.0334; SQL Server 2025, MySQL 8.0.46 and PostgreSQL 18.6; profile Full, 6 measured repetitions per test and database; run from 5 October 2026, 12:12 UTC, to 6 October 2026, 03:09 UTC); `sensitivity-summary.json` belongs to the tuning check run after it. They are published so that every number on the [main page](../../../README.md) can be checked, except the tuning check's per-database medians, which come from the mini-run's own `analysis.json` (not published). The campaign folder itself (`artifacts/benchmark-reports/<campaign id>/`) is git-ignored.

| File | What it is |
|---|---|
| [`analysis.json`](analysis.json) | Every computed result, as written by `scripts/New-PerfDBBenchmarkReport.ps1`: the tie-rule thresholds (`tieRule`), every cell (the 6 analysis-set values per test and database, median, min, max, robust CV, failed saves, deadlocks, retries, CPU per operation), the verdict of every test with its pairwise comparisons and tiers (`verdicts`), the family index and summary word per database (`families`), the derived values (scaling, hot-item penalty, 1 → 8 worker speed-up) and the diagnostics (drift, outliers, settle time-outs, the rehearsal checks, residue tables). Byte-for-byte the same as in the campaign folder. |
| [`README-results.md`](README-results.md) | The README fragments generated by the same script, each marked `<!-- fragment:NAME -->`. The main page pastes them verbatim (tables, verdicts, correctness and concurrency lists, appendix). Two changes from the campaign folder's copy: the chart links point to [`../../images/2026r2/`](../../images/2026r2/) instead of `charts/`, and one local folder path (where the helper scripts and backups were kept) is replaced by a placeholder. |
| [`report.html`](report.html) | The full self-contained HTML report of the campaign (inline styles and charts, no scripts), renamed from `PerfDBBenchmark-158169ad-ebb1-4c0a-920d-84a8eb311cea.html`; the same local folder path is replaced by a placeholder, nothing else is changed. Download it and open it in a browser. |
| [`sensitivity-summary.json`](sensitivity-summary.json) | The summary of the optional tuning check (E11), run after the campaign on 6 October 2026 (17:32–19:36 UTC) as the separate mini-run `36afb400-6a15-407c-964c-56128df64b43`: the engine it covered (`engine`: MySQL, the engine with the most tests at 1.3× or more of the fastest), the threshold (`threshold`: 1.3), the measured repetitions (`repetitions`: 3), each of the five MySQL settings with the value applied (`applied`), its cited sources (`source`) and its value before the check (`before`), and for each of the 11 flagged tests MySQL's median relative to the fastest engine's in the campaign (`mainRelToFastest`) and in the mini-run (`tunedRelToFastest`), the number of valid mini-run runs (`tunedNValid`, 3 everywhere) and the answer (`wouldTuningChangeThis`, always marked "indicative"). Byte-for-byte the same as `sensitivity/sensitivity-summary.json` in the campaign folder. Indicative only and never used in a verdict; the main page reports it under "Would tuning change this?", and [docs/TECHNICAL.md](../../TECHNICAL.md#optional-tuning-check-e11-mysql) gives the procedure, the per-database medians and the caveats. |

The charts used on the main page are the campaign's own SVG files, copied unchanged to [docs/images/2026r2/](../../images/2026r2/).

**`README-results.md` is the generator's raw output, not the published text.** The main page pastes these parts of it verbatim: the at-a-glance table with its "index over" lines, each family's results table, correctness list, concurrency details and CPU-share line, the hot-item table, the correctness table, Table 4, the list of environment changes and the methodology appendix; the decision-guide bullets are pasted with one sentence (MySQL's isolation level) reworded. The other fragments (how we measured, the environment tables 1 and 2, limits, not measured, the glossary and the family introductions) are the generator's drafts: the main page replaced them with reviewed text, so where their wording differs (for example, Block D "on a second night", while the campaign ran back-to-back), the main page is the published version. Bracketed items such as "[… look up and cite]" are placeholders that the generator leaves for the editor; the main page fills them with sourced facts.

Not included: the 21 MB campaign JSON (every run with its raw timings, per-process CPU counters and environment captures), the other campaign-folder files (environment captures, table counts, decision records, check results) and the tuning check's own mini-run files (its campaign JSON, `analysis.json`, HTML report and suite log, under `sensitivity/36afb400-6a15-407c-964c-56128df64b43/`; the per-database medians quoted for the tuning check come from that `analysis.json`). They are described in [docs/TECHNICAL.md](../../TECHNICAL.md#output-files), and the facts taken from them are disclosed on the main page and in [What happened during the campaign](../../TECHNICAL.md#what-happened-during-the-campaign).

To rebuild these files from the campaign JSON into a separate folder (so the campaign folder's own copies stay untouched):

```powershell
.\scripts\New-PerfDBBenchmarkReport.ps1 -InputJson artifacts\benchmark-reports\<id>\PerfDBBenchmark-<id>.json -Publish -OutDir <scratch folder> -ChartUrlPrefix '../../images/2026r2/'
```

The prefix `../../images/2026r2/` gives the chart links of the copy in this folder; the main page uses `docs/images/2026r2/`. The rebuilt files carry their own generation time (`generatedAtUtc` in `analysis.json`).

The verdicts follow the tie rule stated on the main page ([How we decide "faster"](../../../README.md#how-we-decide-faster)); the exact rule is in [docs/TECHNICAL.md](../../TECHNICAL.md#winner-and-tie-rule-formal-version).
